Wearing the right hat

State which hat you are wearing at the start of a session, and do not mix two in one session. The hats exist so that a planning decision and an implementation decision never get made in the same breath.

HatOwns
FounderStrategy, OKRs, epic approvals, sunset decisions
PMInbox → backlog refinement, board updates
DevCode, tests, story status Ready → Active → Review
QATestplan execution, bug raising, sign-off

Mode — the hats enforced across chats

Hats are a convention; Mode is the enforcement. It is a project-global setting that persists in .tandem-mode.json and is injected into every joined chat by a prompt hook.

/tandem:mode plan      # Founder / PM / QA-planning work
/tandem:mode dev       # Dev / QA-execution work
/tandem:mode dual      # both, deliberately
/tandem:mode neutral   # no enforcement

Ask for something out of Mode and Tandem nudges — switch, go dual, or do it as a one-off. It never hard-blocks. Mode resets to neutral automatically when a phase closes.

The two gates

Definition of Ready — before work starts

A story cannot go in-progress until all of this holds:

  • a paired testplan exists, with every acceptance criterion mapped to a test case;
  • every test case has a runnable Command: Claude can execute unattended;
  • dependencies are done or scheduled;
  • an estimate is set;
  • risks are written down.

Definition of Done — before work ships

A story cannot reach done until:

  • every acceptance criterion is ticked;
  • the testplan has been run and all test cases pass, or each failure links to a filed bug;
  • project quality gates pass;
  • the AI-code review is recorded in frontmatter;
  • completed_at is set in the same edit as the status flip;
  • the board is updated in the same response;
  • decisions became ADRs and new tech debt became backlog entries.

When a gate fails

It is supposed to. The gate stopping is the product working, not an obstacle to route around. What to do:

  1. Read the listed gaps. Both gates report exactly which items failed — they never fail

    2. vaguely.

  2. Fix the gap, not the gate. If the DoR complains that a test case has no runnable command,

    3. write the command. Do not loosen the criterion.

  3. If the criterion itself is wrong, change the story and say so — that is a legitimate

    4. scope decision, and it becomes an ADR if it is non-obvious.

  4. Never hand-edit status: to skip a gate. The status enum is a closed set of nine values

    5. (not-started, ready, in-progress, in-review, done, blocked, wontfix, duplicate, archived) and every flip carries a timestamp written in the same edit. A hand-forced flip leaves the board lying about what shipped.

When a test fails

You do not have to ask for a bug report. The moment a test case fails — or a defect is spotted during review or exploration — Tandem writes 34-Bugs/EPIC-NN/FEAT-NN.M/BUG-YYYYMMDD-NN-<slug>.md before the failure is reported in chat. The file carries reproduction steps, an environment snapshot, a first-analysis hypothesis, and a suggested fix direction detailed enough for a junior developer to act on.

Your job is to decide what happens next, not to write the ticket.

When you make a decision

Any non-obvious call — a library choice, a schema field name, a threshold, a scope deferral, a divergence from the defaults — becomes 40-Decisions/ADR-NNNN-<slug>.md in the same response, linked from the story's decisions: array.

The test for "non-obvious" is simple: would a competent person six months from now wonder why you did it that way? If yes, write the ADR. It costs a minute now and saves an archaeology session later.

Common situations

"I don't know what to work on." /tandem:session-start. It reads active work, blocked items, recent decisions and the board, then names the next step.

"This story has grown too big." Split it. An XL estimate is the kit's signal that the story should have been two. Re-run /tandem:split-into-stories on the feature and let the oversized story become several.

"The board is out of date."

npm run pm:all   # lint → monitor → dash → docs

pm:monitor recomputes counts from real story statuses, so the board cannot drift from the files. Normally the Stop hook does this for you.

"Lint is failing and I don't know why." npm run pm:lint names the rule and the file. The most common causes are an invented status value, a status flip without its timestamp, or a story whose paired testplan is missing.

"I upgraded the plugin and something broke." Restart the Claude Code session — until you do, hook errors mentioning the old version's cache path are expected. Then run npm run pm:update inside the project to refresh kit-owned files non-destructively, and npm run pm:doctor to confirm the wiring.

"I want to know if a change is safe before I commit it." /tandem:peer-review — an on-demand review of a diff, branch, PR or file, reporting blocker / major / minor findings.

"I want the plan run without me sitting here." /tandem:autopilot. It drives phase → batches → close unattended, checkpoints as it goes, halts on any failure, pauses near your Claude usage limit and resumes when the window resets.

"Which of my installed skills and agents actually fit this project?" /tandem:curate-toolkit ranks them HIGH / MED / LOW against your project type and writes the overlays into 97-AI-Reference/.

What not to do

  • Do not invent a status value. Nine, closed set, no exceptions.
  • Do not move a story between folders. A story file stays where it was created from

    • not-started through archived; only status: changes.

  • Do not create a story without its testplan. They are written in the same response, by

    • design — a story with a deferred testplan is a story with no definition of correctness.

  • Do not redraft artefact headings from memory. Every new artefact starts from its template

    • in 91-Templates/.

  • Do not let an epic exist without strategic linkage. If you cannot name the OKR or PRD

    • section it moves, the epic is not ready to be written.
