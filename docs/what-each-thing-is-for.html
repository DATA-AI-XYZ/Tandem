What each thing is for

A per-item lookup: every standard folder, every standard item that ships inside it, and every script gets one plain-English line — what it's for, or when you'd open it. If you've ever opened DAILY-WORKFLOW (or any other file in this kit) and wondered what it was actually meant to do, this page is the answer.

Two related pages cover similar ground at a different altitude: Overview explains *why* the kit works the way it does, and the repo-root CODEBASE-MAP.md gives a lightweight, auto-generated table of just the top-level directories. This page is the complete, hand-curated, per-item version — see ADR-0080 for why it lives here rather than being folded into either of those.

Folders

_00-Project-Management/ folders

  • 00-Strategy — the vision, the quarterly OKRs, the customer journey, and the risk register;

    • open it to see why a body of work is happening at all.

  • 10-Inbox — quick, unrefined capture for a new idea or note before it's been thought through;

    • open it to jot something down without stopping to structure it.

  • 11-Backlog — refined items that are worth doing but not yet ready to start; open it to see

    • what's queued and prioritised.

  • 12-Active — the live "what's in flight right now" index (ACTIVE.md); open it to see what's

    • currently being worked on, at a glance.

  • 14-Retros — the monthly look-backs on what went well and what didn't; open it before planning

    • the next stretch of work.

  • 20-Requirements — the actual specs (PRDs) describing what's being built and why; open it

    • before starting anything non-trivial.

  • 30-Epics — the big bodies of work the project is organised into; open it to see the

    • top-level roadmap.

  • 31-Features — each epic broken into shippable slices; open it to see what a given epic is

    • actually made of.

  • 32-Stories — the individual, workable units of work, one file per story, each carrying its

    • own status; open it to find or pick up a specific piece of work.

  • 33-Testplans — one test plan per story, proving the story actually works; open it to see how

    • a story gets verified before it's called done.

  • 34-Bugs — defects that were found and logged, with reproduction steps; open it to see what's

    • broken right now and how to reproduce it.

  • 40-Decisions — the record of non-obvious calls made along the way, and why; open it before

    • re-litigating a decision that's already been made.

  • 41-Reports — generated snapshots, audits, and side-by-side comparisons; open it for a

    • point-in-time view rather than the live plan.

  • 42-Monitor — the single board with overall status, counts, and revision history

    • (MONITOR.md) plus the generated dashboard; open it for the one-page state of the whole project.

  • 90-Standards — the rulebook for how the process itself works, day to day; open it whenever

    • you're unsure how something is supposed to be done. See Standards below for what's inside.

  • 91-Templates — the starting shape for every new file of a given type; open it before creating

    • a new artefact by hand. See Templates below.

  • 92-Prompts — ready-to-use prompts for each step of the lifecycle; open it if you want to

    • trigger a step outside the usual skill commands. See Prompts below.

  • 93-Scripts — the small, dependency-free programs that check, build, and render the plan;

    • open it to see what each npm run pm:* command actually runs. See Scripts below.

  • 97-AI-Reference — notes on which installed AI tools are worth reaching for on this project and

    • which aren't (written by the curate-toolkit skill); open it before picking a tool, to see if it's already been rated for this project type.

Top-level directories

  • skills/ — the packaged, step-by-step instructions Claude loads for each part of the process

    • (drafting, executing, closing out, and so on); open it to see or change how a lifecycle step behaves. See Skills below.

  • hooks/ — small checks that fire automatically at specific moments in a Claude Code session

    • (after a file is edited, when you send a message, when the session ends); open it to see what runs on its own and when. See Hooks below.

  • .claude/ — Claude Code's own local session and worktree state for this repo; you won't

    • normally need to open it.

  • .claude-plugin/ — the manifest that makes this kit installable as a Claude Code plugin (its

    • name, version, and marketplace listing); open it only if you're changing how the kit is packaged or distributed.

  • docs/ — the published, public-facing site build plus longer-form recommendation notes; open

    • it to see what actually gets published, as opposed to the working source.

  • documentation/ — the narrative documentation set you're reading right now, rendered to

    • browsable pages by npm run pm:docs; open it to understand a concept rather than to look up a single task.

Standards

Every file in _00-Project-Management/90-Standards/:

  • SOP — the standard operating procedure: the full lifecycle, the Definition of Ready and

    • Definition of Done checklists, and the weekly/monthly cadence; open it when you need the actual rule, not just the name of the folder it lives in.

  • PROJECT-CONTEXT — this project's specific stack, conventions, and known quirks; open it

    • before running a build, lint, or test command so you're running the right one for this repo.

  • DAILY-WORKFLOW — a plain walk-through of what a normal day working with the kit looks like;

    • open it if you're not sure what to do next, right now.

  • CLAUDE-CODE-CONFIG — a map of how Claude Code itself is configured for this project

    • (settings, permissions, hooks); open it if Claude Code's behaviour in this repo seems off.

Templates

Every file in _00-Project-Management/91-Templates/:

  • ADR.template.md — the starting shape for a new decision record; copy it when you're about

    • to make a call worth remembering.

  • AI-CODE-REVIEW.template.html — the shape of an AI code-review report attached to a story;

    • used when a story's code changes get reviewed.

  • BACKLOG.template.md — the starting shape for a new backlog item; copy it when capturing

    • something worth doing later.

  • BUG.template.md — the starting shape for a bug report, written so a junior developer can

    • reproduce it in minutes; copy it the moment a defect is found.

  • CLAUDE-SETTINGS.template.json — a conservative default .claude/settings.json with

    • destructive-command guard rails; copy it into a new project so risky commands need explicit confirmation.

  • CLAUDEIGNORE.template — sensible default exclusions for a .claudeignore file; copy it to

    • keep build output and dependencies out of Claude's context.

  • CODEBASE-MAP.template.md — the starting shape of the top-level directory map; used the first

    • time CODEBASE-MAP.md is generated for a project.

  • DIAGRAM-CHEATSHEET.md — copy-paste-ready Mermaid and SVG diagram examples; open it when a

    • decision or spec needs a picture, not just prose.

  • EPIC.template.md — the starting shape for a new epic; copy it when a strategic bet is big

    • enough to need its own body of work.

  • EXPLORATION.template.html — a side-by-side comparison page for weighing three or more real

    • options before a decision; used when a call is too close to just write the ADR straight off.

  • FEATURE.template.md — the starting shape for a new feature inside an epic; copy it when

    • splitting an epic into shippable slices.

  • HTML-ARTEFACT.template.html — the generic shape for a one-off HTML artefact that isn't

    • covered by a template above; copy it for a bespoke report or page.

  • INBOX-ACTION.template.md — the shape of an inbox item that's waiting on a decision from you;

    • used when something needs your input before it can move forward.

  • PRD.template.md — the shape of a Product Requirements Document; copy it when an idea needs

    • proper spec'ing before epics get cut from it.

  • RELEASE.template.md — the shape of a release note or milestone bundle; copy it when a batch

    • of work is about to ship together.

  • RETRO.template.md — the shape of a monthly retrospective; copy it (or let the monthly-retro

    • skill fill it in) at the end of the month.

  • ROOT-CLAUDE.template.md — the starting shape of a project's root CLAUDE.md; copy it when

    • setting up Claude's always-on context for a new repo.

  • STORY.template.md — the starting shape for a new story; copy it when a feature is broken down

    • into individually workable pieces.

  • SUBDIR-CLAUDE.template.md — the starting shape of a folder-scoped CLAUDE.md that only loads

    • when you're working in that folder; copy it for context that shouldn't be paid for on every task.

  • TESTPLAN.template.md — the starting shape for a new test plan, always paired with a story;

    • copy it in the same breath as the story it tests.

Prompts

Every file in _00-Project-Management/92-Prompts/:

  • 01-draft-okrs-from-northstar.md — kicks off drafting quarterly OKRs from the North Star; use

    • it at the start of a quarter, or whenever the current OKRs feel disconnected from the real work.

  • 02-draft-epic-from-okr-or-prd.md — turns an approved OKR or PRD into a new Epic; use it when

    • a strategic bet needs to enter the work graph.

  • 03-split-epic-into-features.md — breaks a reviewed Epic into Features; use it once an epic

    • exists and is ready to be broken down.

  • 04-split-feature-into-stories.md — breaks a Feature into Stories with their paired test

    • plans; use it when a feature is ready to become concrete, workable pieces.

  • 05-refine-backlog-to-ready.md — runs the Definition of Ready checklist on a backlog item or

    • story; use it on the Friday review, or any time before pulling something into active work.

  • 06-execute-story.md — starts work on a Ready story; use it during the daily check-in, the

    • moment a story moves into active work.

  • 07-run-testplan.md — verifies a story against its paired test plan; use it once a story flips

    • to in-review.

  • 08-close-out-story.md — runs the Definition of Done gate on a finished story; use it once its

    • test plan is fully passing.

  • 09-weekly-monitor-update.md — updates the MONITOR board for the week; use it on the Friday

    • review.

  • 10-monthly-retro.md — runs the monthly retrospective; use it on the first Monday of the

    • month.

Scripts

Every *.js directly in _00-Project-Management/93-Scripts/, dependency-free (Node stdlib only), with the npm run pm:* script that invokes it (from this repo's package.json) where one exists:

  • batch-check.js (npm run pm:batch-check) — checks whether a set of stories is safe to run in

    • parallel, i.e. no two of them touch the same files; run it before fanning a batch out concurrently.

  • claude-audit.js (npm run pm:claude-audit) — reports how well CLAUDE.md coverage matches

    • the repo's real structure; run it to see what's covered, incomplete, missing, or excluded.

  • claude-scaffold.js (npm run pm:claude-scaffold) — creates or merges CLAUDE.md files

    • across a repo's detected boundaries; run it to bootstrap or refresh the context layer.

  • doctor.js (npm run pm:doctor) — a read-only health check for the kit's wiring in this

    • project; run it when something about the setup feels half-installed.

  • generate-backlog-board.js (npm run pm:board) — builds an interactive HTML board for

    • prioritising the backlog; run it to get a visual view of what's queued.

  • generate-codebase-map.js (npm run pm:map) — builds and refreshes CODEBASE-MAP.md, the

    • lightweight top-level directory map; run it after adding or removing a top-level folder.

  • generate-dashboard.js (npm run pm:dash) — builds the interactive Command Center dashboard

    • from the live plan; run it after any status change so the board stays current.

  • generate-docs.js (npm run pm:docs) — renders every documentation/*.md (including this

    • page) into a matching *.html; run it after editing anything in documentation/.

  • generate-monitor.js (npm run pm:monitor) — recomputes MONITOR.md's counts and rollups

    • from the real story statuses; run it after creating or deleting artefacts.

  • hook.js (internal/library — not wired to a top-level pm:* script; invoked directly by

    • hooks/hooks.json) — the single cross-platform entry point Claude Code's own hooks call into; you won't normally run this by hand. See Hooks below.

  • install-hooks.js (internal/library — wired as pm:claude-hooks in 93-Scripts/package.json,

    • not at the project root) — copies the kit's pre-commit hook into the host repo's git hooks folder.

  • install.js (npm run pm:install) — wires the kit into a new project: merges the pm:*

    • scripts in, seeds the folder tree, registers hooks, and builds the first dashboard.

  • mode.js (internal/library — wired as pm:mode in 93-Scripts/package.json, not at the

    • project root) — reads and writes the project's conversation-mode state (Plan / Dev / Dual / Neutral).

  • smoke-dashboard.js (npm run pm:smoke) — a headless-browser smoke test proving the generated

    • dashboard actually loads and renders.

  • test-mode-hook.js (internal/library, dev-only self-test) — checks that the mode banner shows

    • up correctly for a joined session and stays silent for an un-joined one.

  • test-mode.js (internal/library, dev-only self-test) — self-tests mode.js's own read/write

    • behaviour.

  • test-monitor-parser.js (internal/library, dev-only self-test) — self-tests the frontmatter

    • parsing that generate-monitor.js relies on.

  • test-pm-paths.js (internal/library, dev-only self-test) — self-tests how the kit detects a

    • project's folder layout.

  • update.js (npm run pm:update) — refreshes only the kit-owned files (templates, standards,

    • tooling) in an already-installed project, without touching your own work.

  • usage-capture.js (internal/library — not yet wired to a top-level pm:* script) — reads

    • Claude Code's own session transcripts and attributes their token usage back to the story or batch that produced it.

  • validate-frontmatter.js (npm run pm:lint) — lints every artefact's frontmatter against the

    • rulebook; run it before trusting a status or a timestamp on the board.

  • purpose-guard.js — keeps the what-each-thing-is-for reference honest: warns (never fails) when something in the kit lacks its purpose line, and can append fill-me stubs for new items. No direct npm script; surfaced through npm run pm:doctor.
  • usage-governor.js — the decision brain for hands-free runs: given how much of the usage window is spent, it says continue, pause before the next batch, pause now, or stop and ask. No direct npm script; consulted by the autopilot flow.
  • usage-reconcile.js — compares what a story was estimated to cost in AI usage against what it actually cost, and suggests estimates for new work from history. No direct npm script; run with node when reviewing spend.

Skills

Every directory under skills/. Each line is harvested from that skill's own description: frontmatter in its SKILL.md, not rewritten:

  • close-out-story — Close out a STORY through the Definition of Done gate.
  • autopilot — Run the whole delivery plan end-to-end without supervision: it opens each phase, runs every batch in its own fresh context, saves progress, pauses near the usage limit, and resumes on its own.
  • close-phase — Close out a whole phase after an execution-strategist chat / execute-batch run

    • finishes — gate on every phase story being done, compile a phase retrospective, capture follow-ups, update the board, then run a gated merge to main.

  • core — Core PM Operating Kit rules — closed-set status enum, frontmatter timestamps,

    • Story-Testplan pairing, DoR/DoD gates, hat protocol, ADR-on-the-spot, bug-auto-raise.

  • critique — Advisory artefact quality review for planning artefacts (Epic, Feature, Story,

    • Testplan).

  • curate-toolkit — Rank installed AI tools (Skills, Agents, Commands, Plugins) by fit for this

    • project and write relevance overlays under 97-AI-Reference/.

  • document — Author the project's default markdown documentation set from accumulated PM

    • knowledge.

  • draft-epic — Draft a new EPIC from an OKR key result or a PRD section.
  • draft-okrs — Draft quarterly OKRs from a North Star.
  • draft-prd — Draft a Product Requirements Document from a North Star, an OKR Key Result, raw

    • founder notes, or a BACKLOG entry that needs more spec.

  • execute-batch — Execute one "chat" from an Implementation Strategy in this fresh session —

    • run its stories sequentially (execute-story → run-testplan → close-out-story) with atomic per-story finalisation, a context-budget guard, and clean failure recovery; then flip the chat's executed flag so the dashboard shows it done.

  • execute-batch-parallel — Execute one "chat" from an Implementation Strategy by fanning out one

    • scoped sub-agent per Ready story IN PARALLEL, then reconciling the board once on the main thread.

  • execute-story — Start work on a Ready STORY.
  • execution-strategist — Plan how to execute a whole epic — group its stories into "chats" that

    • are genuinely good to run together, the way a lead plans a sprint.

  • fill-claude-md — Fill in or trim a CLAUDE.md so only non-discoverable, project-specific,

    • broadly-relevant lines remain — the judgement layer applying the three content-economics tests over pm:claude-scaffold's stubs.

  • install — Wire the Tandem PM kit into a project — materialize the full folder tree + seed

    • files from the manifest, pin the folder layout, merge the pm:* scripts, guard-register hooks, and generate the Command Center dashboard.

  • mode — Set and enforce the project's global conversation Mode (Plan · Dev · Dual · Neutral) —

    • the persistent "moat" that frames every joined chat.

  • monthly-retro — Run the monthly retrospective.
  • path-scope-example — Reference example of a PATH-SCOPED skill (ADR-0010).
  • peer-review — On-demand code peer review of an explicitly-scoped target.
  • refine-backlog — Refine a BACKLOG item or not-started STORY by running the SOP §6 Definition

    • of Ready checklist.

  • reflect — End-of-session reflection that proposes updates to CLAUDE.md / SOP.md /

    • PROJECT-CONTEXT.md based on what happened.

  • run-testplan — Run every test case in a TESTPLAN.
  • session-start — Load active project context at the start of a Claude Code session.
  • split-into-features — Split an EPIC into Feature files.
  • split-into-stories — Split a Feature into Stories AND paired Testplans in the same response.
  • start-phase — Open a phase — the opener counterpart to close-phase.
  • update — Pull Tandem kit improvements into an already-installed project without touching your

    • work — refresh only kit-owned files (templates, standards, tooling) + regenerate the dashboard, never the operator's artefacts or folder structure.

  • weekly-monitor — Weekly MONITOR update (Friday cadence).
  • write-outcomes — Dispatched by producer skills via a sub-agent to turn an artefact's

    • technical content into one plain-English founder-outcome line; it is not a manually-invoked lifecycle command.

Hooks

Everything registered in hooks/hooks.json. All three route through the same cross-platform entry point, 93-Scripts/hook.js (so behaviour is identical on Windows, macOS, and Linux), dispatched by event name:

  • PostToolUse (hook.js post-tool-use) — after any Write or Edit tool call, if the touched

    • file sits under _00-Project-Management/, automatically lints its frontmatter and surfaces any violation back into the session.

  • UserPromptSubmit (hook.js user-prompt-submit) — on every message you send, if the session

    • has joined conversation Mode, prints the mode banner into context; otherwise stays silent and never blocks the prompt.

  • Stop (hook.js stop) — at the end of a session, if anything under _00-Project-Management/

    • changed, automatically regenerates the dashboard (and, only if enabled, adds a one-line nudge about an incomplete CLAUDE.md — advisory only, never blocking).
